# Telegram quality reactions

Quality reactions are optional and disabled by default. They inspect one completed print run; they never book stock, deliveries, invoices or shipments. Existing notification links, quiet hours, daily digests and the mixed-quantity dialog continue to work.

1. Enable PrintOps authentication and sign in as an administrator. Create a Telegram notification provider with a bot token and a **numeric** chat ID. Enable quality confirmation notifications.
2. Use a dedicated bot with no other `getUpdates` consumer. Make the bot a chat administrator. Telegram only delivers individual `message_reaction` updates when the bot has this role. A bot can have only one configured reaction provider in PrintOps (including disabled configurations).
3. Expand the provider settings. Under **Telegram quality reactions**, enter one `Telegram user ID=PrintOps user ID` per line. Use numeric user IDs, not usernames or chat IDs. Confirm the IDs with the people concerned. Obtain the local user ID from user administration/API. Save with **Enable quality reactions** selected. Removing a line revokes that user's reaction access. Changing trusted bindings, reaction activation or provider routing/configuration invalidates outstanding reaction prompts, including messages still being sent. New prompts are required after such edits. The mapping also stores the account's nonreused identity: deleting and recreating an account never transfers access, even if SQLite reuses its numeric ID. Remove a stale mapping before explicitly binding a replacement account.
4. On a new quality prompt, add exactly one reaction: 👍 means all intended parts are good; 👎 means all intended parts are rejected. For mixed quantities use the PrintOps link and normal inspection dialog. The first valid answer within the prompt's 48-hour lifetime wins. Changing or removing the reaction never undoes an answer. Existing link/dialog answers also prevent a later reaction from overwriting them.

New archives store the owner’s nonreused account identity at creation or explicit ownership change. Legacy archives are not backfilled from ambiguous numeric IDs. An own-only user cannot confirm a legacy archive through reactions; use the existing authenticated browser dialog, or an authorized all-scope operator.

Only a trusted active user with current archive update permission and access to both the archive's and run's printers can answer. Own-only users must still own the same archive under the same account identity. Anonymous administrators, reaction counts, bot actors, custom emoji and ambiguous reactions cannot authorize an inspection. Turning off authentication, the provider, quality notifications or reactions prevents processing. Configuration does not grant additional archive permissions.

Bindings are made only for a successfully sent concrete positive Telegram message ID and the exact current completed run, token, quantity and expiry. A scheduled message with ID zero cannot authorize reactions. Historical-run prompts and prompts without a current confirmation token remain usable through the normal authenticated browser dialog; reactions do not apply to them. Duplicate or expired updates cannot overwrite existing outcomes. If a message was sent but saving its binding fails, use the browser link.

PrintOps polls outbound with explicit `allowed_updates=["message_reaction"]`, a database-backed lease and a durable cursor. It commits each decision and cursor before sending the acknowledging next offset. A crashed worker's lease expires after 60 seconds. After six idle days it omits the stale offset because Telegram may randomize update IDs after a week. Telegram retains updates for at most 24 hours, so long outages can lose reactions; use the dialog when necessary. The existing token and first-answer checks remain authoritative even when updates are delivered again.

An existing webhook is preserved: **Webhook active: polling paused** means no polling occurs. PrintOps never deletes or changes a webhook. Transport errors and polling conflicts use a five-minute retry delay and report a generic status without bot tokens or webhook URLs. Arrange exclusive bot ownership externally before enabling this feature; PrintOps cannot detect every other external poller before Telegram reports a conflict. Disabling reactions does not automatically restore another application's polling configuration.

Primary Bot API contracts checked for this implementation: [Update](https://core.telegram.org/bots/api#update), [MessageReactionUpdated](https://core.telegram.org/bots/api#messagereactionupdated), [getUpdates](https://core.telegram.org/bots/api#getupdates), [getWebhookInfo](https://core.telegram.org/bots/api#getwebhookinfo), and [MessageId](https://core.telegram.org/bots/api#messageid). Tests use fake Bot transport; no real notifications or bot configuration changes are required.

Reaction decisions hold a configuration revision lock through outcome/cursor commit. If a revocation wins that lock first, the old prompt cannot answer; otherwise the in-flight answer finishes before revocation returns. No network request runs under this lock.

Accepted reactions remove their binding in the outcome transaction. The worker checks for expired bindings at startup and on a five-minute cleanup schedule, including disabled providers. Unanswered bindings are eligible for removal after the prompt's 48-hour validity. In-flight polling work can delay the next cleanup; downtime delays it until startup. Lookup and expiry indexes are installed for existing databases too.

An untouched settings form follows server refreshes. Explicit unsaved edits remain in the form until saved; saving intentionally submits those edits. Controls are temporarily disabled during saving.
