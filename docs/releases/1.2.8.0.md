# PrintOps 1.2.8.0

Release preparation following 1.2.7.9. The version is not published by this
document or by merging a preparation PR. The complete change list is in
[CHANGELOG.md](../../CHANGELOG.md).

## Highlights

- Quality confirmation for individual print runs, including Telegram; batch
  targets and reprinting stay separate from inventory and deliveries.
- Material numbers, configurable spool labels, partial label sheets, stock-break
  and low-filament notifications, with existing procurement/reservation identity.
- Image/PDF/spreadsheet/STEP previews, library links/photos, STL-to-3MF composition
  and plate-object selection.
- Connected applications, scoped app notifications, a streaming camera overlay
  and theme messages for embedded apps.
- Orca presets and an optional native OrcaSlicer sidecar for Linux ARM64/AMD64.
- Updated native-sidecar build dependencies with full pre-build and pruned
  production audits; the wrapper application, engine and runtime dependency
  artifacts retain their existing versions.
- Account-scoped inventory and printer-card preferences, camera placement and
  authorized next-job previews, plus the completed Dutch interface.
- Guarded drying, bed keep-warm, calibration contexts, project groups and printer
  media downloads; existing PrintOps commerce workflows remain available.

## Upgrade notes

Create a full backup before upgrading; follow [UPDATING.md](../../UPDATING.md)
for the installation type. Database migrations run at startup. Preserve the
existing database, uploaded files, document assets, configuration and secrets.
Do not replace a live data directory with the repository contents.

Docker and Windows installers build their frontend and stage the pinned PDF
runtime. Native updater scripts rebuild the frontend when `npm` is available;
the repository also retains a freshly built `static/` delivery bundle for the
existing native in-app update path without `npm`. Editable frontend source and
assets remain in `frontend/`. See [repository layout](../repository-layout.md).

Native installations also need the verified PDF runtime described in
[PDF runtime updates](../pdf-runtime-updates.md). Check document-render readiness
after restarting; previews are not a substitute for successful validation of
final issued documents.

Account-scoped preferences need a verified account and, for printer preferences,
a stable hardware serial. Older unscoped camera defaults/open-overlay lists are
not migrated into account storage and may need to be chosen once again.

Manually started or ambiguously owned drying runs are protected from automatic
stop/pause. This can delay queued jobs. When firmware already reports `IDLE`,
selection can proceed without first sending a drying-stop command. This is the
explicitly selected manual-drying priority; see
[scheduled AMS drying](../scheduled-ams-drying.md) and
[the integration register](../optional-upstream-implementation-2026-10-14.md).

## Boundaries

- Classic AMS and external Sunlu dryers do not gain supported automatic daily
  drying. Firmware/device capabilities still determine available controls.
- ARM64 sidecar support is for OrcaSlicer on Linux. Bambu Studio ARM64 support
  and a measured 2 GB RAM operating guarantee are not included.
- A next-job preview is an authorized snapshot, not a dispatch guarantee.
- The PostgreSQL pool warning considers one worker rather than every client.
- Quality confirmation does not automatically create stock or delivery postings.
- Twelve UI locales do not expand commercial document output beyond German and
  English. MakerWorld is the implemented provider behind the new provider API.
- Software/container checks do not establish physical printer, camera, heating
  or firmware acceptance. Windows installers remain explicitly unsigned.

## Publication checklist

1. Review the preparation PR and its complete checks. Confirm both the final PR
   head and the post-merge main run; retain failed or cancelled historical runs.
2. Confirm the final version/date in the changelog and that source fallback,
   Python package and default Docker build version all match `1.2.8.0`. Release
   tags stamp container/Windows runtime versions; the private frontend tooling
   package version is not the application release version.
3. Perform any installation/device acceptance required for the deployment. Take
   a backup before updating a live installation.
4. Publish only after the release decision. Pushing `v1.2.8.0` starts the existing
   container and Windows release workflows; it is a publication action. Review
   their actual artifacts, checksums, unsigned notice and attestations using
   [release integrity](../release-security.md).

Preparing these files does not create a release tag, publish a GitHub release or
container image, deploy an installation, or send a command to a printer.
